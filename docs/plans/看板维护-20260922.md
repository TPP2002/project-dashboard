### 复述与第一轮实验

- 自检自行随机选择高位端口并直接启动，既不知道系统是否允许绑定，也不持有该端口；并发启动还可能撞上别人的服务。改为服务自身 `listen(0)` 持有系统分配的端口，用子进程 IPC 告知自检父进程实际地址，再通过 HTTP 校验 PID。普通固定端口的复用、升级行为不变。涉及 `packaging/build-installer.cjs`、`server/server.cjs` 与端口隔离测试，已追加认领文件域。
- 假设：端口 0 当前虽可监听，但 `tryListen` 把申请值当作实际地址，且仍扫描 0～8；新增两份真实服务测试应因地址为 0 失败。修改后两进程应各自有非零、不同的监听地址。
- 撤单假设：`runScheduled` 只按 `completed` 决定撤单，没有识别 `waitFor` 已返回的终态，也没有在撤单拒收后核实状态。新增测试应复现多余撤单与误报警；修复后真实终态不报警，仍运行或读取失败仍报警。
- 边界：启动失败/缺模块仍报错，超时仍销毁本次子进程；IPC 只传服务签名与端口，不传私有数据；状态无法确认不当作撤单成功。两处均先红后绿，不重试 CI 来掩盖原失败。

### 根因三问（修复前设计）

1. 原因：手选端口没有系统分配保证；排队包装未区分失败退出与已收终态。
2. 改法：把监听与端口占用放在同一子进程完成；按客户端实际终态回执处理撤单。
3. 影响：端口 0 仅用于显式自检；固定端口、数据根隔离、同实例升级保留。撤单不确定时保持可见报警，任务失败的退出码保持原值。
