# COST-UI-SESSION-DETAIL 施工记录:成本页补出「每个对话」与「每张工单」两张明细表

工单要求:成本监管页此前只能看「按天 / 按模型 / 按项目」的汇总,钱花在哪次对话、哪张工单上看不出来。
本单在 `core` 层补聚合与纯函数、在 `server` 层补两条接口、在前端补两张带筛选的明细表,
并按派单方给出的九步顺序逐条落地。本记录只写事实与判断理由;机验(单测、断言复核、
构建)由派单器在主工位统一重跑,施工过程按算力规矩没有自行运行测试。

## 九步对照

1. **fable 缓存读专门价**:`core/costUsage.cjs` 的 `PRICE.fable` 加 `cacheRead: 0.25`;
   `usdActualOf` 改为「条目给了专门缓存读价就用专门价,没给退回 `0.1 × input`」。
   其余四个模型(opus / sonnet-4-6 / sonnet / haiku)的价目一个字节没动。
   折算断言独立复核(没有照抄派单方数字):
   - actual = (10×10 + 1000×0.25 + 50×2×10 + 100×50) / 1e6 = 0.00635
     (无 TTL 细分的缓存写 50 全归 1h 桶,1h 桶单价 2×input = 20/百万);
   - noCache = ((10+1000+50)×10 + 100×50) / 1e6 = 0.0156(noCache 的口径是全部输入按全价,
     与缓存读价无关,所以不跟着 0.25 变);
   - saved = 0.0156 − 0.00635 = 0.00925。
   三条都与派单方给的数一致,才写进 `test/costUsage.test.cjs`。
2. **缓存版本字段改名**:`version` → `schemaVersion`,读缓存严格 `===` 比对,对不上整份丢掉
   全量重扫,不写任何迁移分支。版本号升到 3:缓存里存的结构也变了(去重 + 新增会话·按天明细桶)。
   前科是结构改了没升号,旧缓存被照单全收、新字段全空还不报错——这次名字和号一起换。
3. **按 message.id 去重**:同一条消息因流式输出会有多条记录。边界按工单原文执行:
   只有「id 存在且是非空字符串」的记录参与去重、同 id 只记第一次;
   没有 id / id 为空串 / id 不是字符串(数字等)的一律各算各的全部计入。
   搞反这条,现有夹具里不带 `message.id` 的行会塌缩成一条、老断言当场转红——这条边界是
   工单明示的,照办。
4. **会话明细行**:会话 id、模型(用过多个全列,按输出量降序)、起止时间(窗口内首末记录)、
   轮次(= 去重后的计入条数)、峰值/平均上下文、四类 token、压缩次数、等价美元、所属卡。
   **压缩次数的坑**:压缩标记行(`type=summary` 或 `isCompactSummary`)通常不含
   `"assistant"`,原有的行级预筛会把它们整行扔掉,压缩次数永远是 0。处理:预筛放宽为
   「三选一命中才跳过解析」——只放宽,绝不删(它挡住绝大多数行不做 JSON.parse,删了扫描
   明显变慢)。
5. **两项新指标 + 对账断言**:
   - 「轮次 × 平均上下文」(`context.load`):这个区间一共驮着多少上下文在干活;
   - 「上下文 > 40 万的轮次占比」(`context.heavyRatio`),门槛常量 `HEAVY_CONTEXT_TOKENS = 400000`;
   - 对账断言:**所有明细行四类 token 相加 === 顶层合计**,实扫与缓存命中两种跑法都断言
     (夹具 `reconcile()` 助手)。
6. **筛选纯函数**:`core/costSessionDetail.cjs` 导出 `filterSessions`(日期/模型/卡)、
   `summarizeSessionRows`(筛后合计)、`sessionFilterOptions`(候选项)、`cardForSession`。
   不是只写在 Vue 组件里,node --test 直接机验。
7. **工单明细**:`core/costJobDetail.cjs` 的 `collectJobRows(jobsRoot)` —— jobsRoot 由调用方
   传入(server 侧按注册表解析后拼好传进来),模块内不写死路径、不 require 项目解析器、
   不出现任何盘符。
8. **前端**:`web/src/components/cost/SessionDetailTable.vue` 与 `JobDetailTable.vue` 两张
   明细表(带筛选、筛后合计、空态文案),接进 `CostMonitor.vue`;概览卡里
   「Claude 重复利用省下的钱」从主卡位撤下,降级保留在「花销结构」表里(降级≠删除);
   腾出的位置放上两项上下文新指标卡。
9. **本施工记录**(你正在读的这份)。

## 关键判断与理由

### 上下文口径(C-16,派单方给的可选项里定档)

单轮上下文 = input + 缓存读 + 缓存写(这一轮喂进去的完整提示),**不含输出**。
峰值取该会话窗口内最大单轮;平均 = Σ单轮上下文 ÷ 轮次;轮次 = 去重后计入条数。
理由:三项口径的差别只在「算不算输出、算不算缓存写」,派单方建议档明确说按「喂进去的
完整提示」理解,与「这个会话驮了多大的上下文」的直觉一致;输出是产物不是驮载。

### 「Vue 直接调 core 纯函数」不可行(推翻 C-17 的实现路径,保留其意图)

C-17 原话是筛选逻辑进可机验的纯函数、前端直接调。意图已完整落实:筛选就在
`core/costSessionDetail.cjs` / `core/costJobDetail.cjs` 的纯函数里,机验直接覆盖。
但「前端直接调」在这条流水线上走不通:`web/vite.config.ts` 是禁区文件,其中的虚拟模块
清单没法新增,且其注释明言不允许浏览器直接加载 `.cjs`;因此筛选由 server 侧接口
(`GET /api/cost/session-detail`、`GET /api/cost/job-detail`)调同一批纯函数完成,
前端只收表单、发请求、摆表格。候选项(options)由 server 从「未筛的全集」取,
保证筛完之后下拉框不至于缩没。

### 所属卡判据(推翻 C-18 的「worktree 标记」半条件)

C-18 原案是「cwd 命中 worktree 标记 + 目录名含卡 id」两个半条件。实际落盘事实是:
派单 worktree 的目录名就是卡 id 的小写(如 `.codex/worktrees/cost-ui-session-detail` 对应卡
`COST-UI-SESSION-DETAIL`)。据此判据定为一条更简单的硬规则:**cwd 按分隔符(正反斜杠都算)
切段,某一段不分大小写恰好整段等于某张卡 id 才命中;从最深的段往回找,命中即返回卡 id 原样**。
整段相等才算,子串不算(`t-1-extra` 不命中卡 `T-1`);多段命中取最深;主仓检出目录、
普通项目目录、没有 cwd 的记录一律判不出给 null,不许猜。
理由:半条件的「worktree 标记」在数据里并不总是存在,而「目录名就是卡 id」是派单器
固化的命名契约,单条件判定没有歧义、可机验、误报率更低。

### 「级联链」判据(仓内零先例,自定并说明)

全仓检索没有「级联」的既有口径,只能从落盘事实自定:**同一张卡(taskId)派过多张工单 →
true;没有卡的工单 → null(判不出);同卡只有这一单 → false**。
理由:纯落盘事实、不猜;「一张卡派多单」正是工单语境里「同一件事反复烧钱」的可见形态。
汇总与筛选里该字段只透传展示,不参与任何金额计算。

### 工单人民币:复用,不另立口径

每张工单的人民币直接复用 `core/deepseekCostUsage.cjs` 的 `costRmbOf`(价目表 + 四桶折算)
与 `isPeakBeijing`(高峰判定),只 require、不修改那个冻结模块;token 四桶的解析口径
(含缓存写 TTL 细分)照抄该模块同款判据(其内部函数未导出,故按同形照抄并注释声明)。
「实际判读模型」取最后一条 result 的 modelUsage(只有一个模型时)、退回 result 的
model 字段、再退回日志里最后一条 assistant 的 model;判不出不折钱。
CLI 自报的 `total_cost_usd` 只作展示参考列,**不参与任何计价口径**。

### 积分:没有每单数据源,不造数

工单列的字段清单里有「人民币或积分」。逐单的积分消耗没有任何落盘数据源(工单文件、
执行日志里都没有),造一个数就是造假账。处理:不造数;人民币有数据源(DeepSeek 价目)
就折人民币,判不出的单显示「—」。这一点如果负责人想要积分口径,需要先定数据源,见
「待拍板」。

### 压缩计数不按天窗口化

压缩标记行(summary)常无可靠时间戳,按天窗口会把它们整批丢掉。处理:压缩次数按会话
整份流水计数,不参与窗口过滤;其余字段(四类 token、轮次、上下文)全部窗口化。

### 会话行的窗口化口径(对账恒成立的架构原因)

明细桶按「会话 × 按天」缓存(缓存存全时间范围),出明细行时才按窗口 cutoff 过滤——
这样明细行与顶层合计天然同一窗口口径:凡进了顶层合计的桶必进某条明细行,反之亦然。
「明细行四类 token 相加 === 顶层合计」这条对账断言因此恒成立,漏桶、重复进桶、
旧缓存没作废三类病都会被它当场抓住。跨窗口会话只计窗口内的轮次与 token,
起止时间取窗口内首末记录。

### 去重与缓存、会话归属的交互口径

- 去重在单文件扫描内做(同一条消息的流式重发都在同一份 transcript 文件里);
  跨文件不会误伤:不同会话各有各的 id。
- 同一会话 id 出现在多个文件(如续写文件)时,按会话·按天逐桶合并(数值相加、峰值取大、
  首末时间取小/大);cwd 取最先出现的非空值;压缩次数跨文件相加。
- 子 agent 的 sidechain 消息若与主会话同 sessionId 就并入同一行;有独立 sessionId 的
  就是独立会话行——这是流水落盘的事实口径,不做猜测归并。

### 文案红线口径

工单背景里「`[[占位符]]` 之外的路径一律违规」这类机制在本仓并无对应实现;本仓现行的
红线是 `test/noLocalIdentifiers.test.cjs` 的两道机验(外置名单 + 路径形状检查)。本单全部
新增文本按现行口径执行:不出现本机路径、主机名、真实项目名,夹具一律临时目录 + 合成值。
