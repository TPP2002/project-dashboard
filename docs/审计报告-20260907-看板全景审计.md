## 2. 文献与行业实践对照(只写"对本看板意味着什么")

### 2.1 任务跟踪器正在变成 AI agent 的控制面
- Linear 的模型:**把 issue 委派给 agent,人仍是 assignee 与责任人**;agent 用 `thought / action / elicitation / response / error` 五种活动汇报,10 秒内必须先回一个 thought,30 分钟无活动判为 stale;向人提问用 elicitation(带选项);"不要靠可编辑的评论重建过程,活动是冻结快照"。Jira 在 Team '26 上也把"把工作项直接分派给 Rovo/第三方 agent"做成 GA。
- GitHub Copilot coding agent:把 issue 当 prompt;每个 agent session 有**可实时跟进的会话日志、token 用量、会话时长**,可随时 Stop。
- **对本看板的启示**:
  1. 本看板的 `claim/progress/pending/done` 与 Linear 的 thought/action/elicitation/response 是同构的,`pending` 三件套比 Linear 的 elicitation 更严格——这是差异化优势,**保留并做成机读协议**。
  2. 缺的是 **error/stale 语义**:卡陷在"施工中"无人问津只有 30 分钟黄标,没有"施工方失联/放弃"的动作(`unclaim`),也没有 stale 升级(→ 通知 → 自动可复工)。
  3. Linear 的 "human remains the owner" 对应你的"负责人拍板+验收";看板应把**人→AI 的回话通道**补上(现在人只能拍板,不能留言/追问/要求补信息)。

### 2.2 Kanban 流指标:WIP · 卡龄 · 吞吐 · 周转
- ProKanban 四个基本流指标:WIP、Throughput、**Work Item Age(已开工未完工的卡龄)**、Cycle Time;Little's Law:平均周转 = WIP ÷ 吞吐,压 WIP 是缩短周转最快的办法。业界共识:每周复盘一次,复盘要落到一个决定或实验,而不是看图。
- **对本看板的启示**:每日成果/洞察页已经有 Throughput、CFD、周转分布(这一点做得比多数个人工具好);**缺卡龄(aging)与 WIP 上限**——施工中卡只有"30 分钟没更新"一个二值黄标,看不出"这张卡已经开了 6 天"。看板泳道头应显示 WIP 数与可配上限,卡片显示卡龄分级色。

### 2.3 人在回路审批的设计
- 审批深度按**可逆性与影响**分层:只读工作抽样复核;可逆动作批量审批(10~50 条一次);高影响一条一审;不可逆的人亲自做。给审批者看的必须是"证据 + 预期结果 + 错了的下场";每次驳回要能教会 agent 下次怎么做;要有审计留痕。
- **对本看板的启示**:`pending` 三件套(背景/利弊/推荐理由)正是"证据+预期+下场";已经做对。**缺**:①"信息不完整"徽章只是提示,不能一键要求补齐;②拍板后无法在短时间内撤销;③"驳回并说明"没有通道——只能拍一个自定义答案。

### 2.4 面向 agent 的 CLI 设计与 token 效率
- 行业经验(agentfmt、CLI-vs-MCP 讨论、ClickUp/rdt 等 agent CLI):**shell 命令 5~20 token,MCP 信封 50~200 token**;输出要"紧凑可扫",空值省略、用符号代替句子(✓ ✗ ⚠)、实体一行 `[type] "name" (id)`、层级缩进;统一 flag 命名(`--json/--limit/--page`);窄工具(返回三个结构化字段)优于让 agent 解析原始输出;扁平化+只选必要字段可省 90%+。
- **对本看板的启示**:CLI 路线是对的(相对 MCP 更省);但 `list/show/inbox` 都是"整卡回吐",`--json` 成功返回整个 task 对象;没有 `--help`;没有 `--brief/--fields`。**真正的降本点是"少跑几趟、少读几处"**:今天 AI 开工要读 CLAUDE.md 锚段(≈1.5k token)+ skill §11.9(≈15k 整份触发)+ `precheck` + `show` + `inbox`,并且三份文档互相矛盾会造成白跑(照 CLAUDE.md 示例 `add` 会被 `--model` 机器闸拒收,再来一轮)。

### 2.5 Claude Code 侧的实践
- 社区共识:CLAUDE.md 控制在 ~200 行内,超过后规则被稀释;"必须强制的用 hook/权限,上下文知识用 skill,常驻指导要短"。
- **对本看板的启示**:看板锚段现在 ≈130 行/1.5k token 常驻每个接入项目的每个会话,其中大半是"为什么这么严"的说教;**把"怎么做"做成 `cli protocol` 机读输出、锚段只留 20 行指路**,同时用 hook(已有的 pre-commit 闸门)兜底——这正是"规则进 hook、知识进命令、常驻只指路"。

### 2.6 进度表达:山丘图(Shape Up)
- Basecamp 的洞见:待办计数会随施工增长、估时掩盖不确定性;山丘图把工作分"上坡(还在搞清楚)"与"下坡(照着做)",**不动的点就是举手求助**。
- **对本看板的启示**:AI 施工恰好是"上坡短、下坡长"或反之,`percent` 单值表达不了"卡在不确定上"。可选增强:`progress --phase 上坡|下坡`(一个枚举,不增负担),看板卡用一个小山丘位置替代/补充百分比——**属于外观改动,先出方案**。

### 2.7 游戏化与个性化
- 研究与实践的共识:**forgiving streaks**(允许暂停/宽限日/周末跳过),不要"断一次归零";庆祝动效(彩带、独角兽)显著提升满意度但要能关;"让用户自定义主题/布局,工具就变成个人手作物,粘性更高"。批评者提醒:奖励要对准"有价值的完成",不要奖励"动作多"。
- **对本看板的启示**:连续产出天数已有(🔥 会被换成图标);加"宽限日"规则;完工庆祝、声音、每项目主题色、密度/字号;所有效果默认可关、遵守 `prefers-reduced-motion`。物理 RGB 灯带:Home Assistant/WLED 都能用一条 REST/webhook 调色,看板只需**发事件 webhook**,不必自己认硬件。

## 6. 个性化与趣味功能提案(全部默认可关,先出方案再做)

1. **图标体系替代 emoji**(负责人点名):一套 24px 线性图标(Lucide 风格,ISC 许可,内联 SVG 不引库),状态用"形状+色点"而非 emoji;深浅主题各校一遍对比度。

5. **密度与字号**:舒适/紧凑两档 + 基础字号 13~16px。
6. **声音主题**:拍板 叮、完工 咚、阻塞 低鸣;默认静音,支持静音时段。
7. **桌面通知**:新待拍板/新完工/卡住超时,Notification API,点击直达。
8. **事件 webhook(可选)**:`DASHBOARD_EVENT_WEBHOOK=<url>`,完工/待拍板/阻塞事件 POST 一条 JSON;文档给 Home Assistant `light.turn_on rgb_color` 与 WLED JSON API 示例,物理 RGB 灯带随看板变色(待拍板橙、全绿呼吸、阻塞红)。
9. **山丘图位置**(可选):`progress --phase 上坡|下坡`,卡片小山丘替代/补充百分比,不动的点=求助信号。
